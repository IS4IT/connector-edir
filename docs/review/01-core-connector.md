# 01 — Core connector (`AbstractLdapConnector`)

`src/main/java/com/evolveum/polygon/connector/ldap/AbstractLdapConnector.java` (2,244 lines) is the
template-method base of the connector: it implements the whole ConnId SPI surface the bundle exposes
(`PoolableConnector`, `TestOp`, `SchemaOp`, `SearchOp`, `CreateOp`, `DeleteOp`, `UpdateDeltaOp`, `SyncOp`),
owns the lazily-initialised `SchemaManager`/`AbstractSchemaTranslator` pair, dispatches `executeQuery` to one of
four search shapes (by DN, by UID, secondary-identifier OR, usual), picks a paging strategy, and turns ConnId
attributes and `AttributeDelta`s into LDAP add/modify/moveAndRename/delete requests. The inherited upstream code
(search dispatch, DN handling, GuardedString-late-decryption, connection borrow/return, error translation) is in
good shape and reads as carefully thought through — passwords are logged before decryption on purpose, cursors are
closed with the MID-7091 workaround, and the "return the connection in `finally`" discipline is consistent (and
harmless where it looks like a leak, because `ServerConnectionPool.returnConnection` is a no-op for pooled server
connections). The weak spot is the newer reference/association block (`saturateReferenceAttributeValues`,
`updateAssociationsAttempt`, `getObjectReferenceAttribute`, `reWrapReferenceDeltas`, roughly lines 954–1010 and
1395–1654): it is written defensively in some places and not at all in others, and it fails with bare
`NullPointerException`s on inputs midPoint can legitimately send. All of that code is inert unless
`managedAssociationPairs` is configured, which is what keeps these findings at `major` rather than `blocker`.

No blocker-severity findings.
