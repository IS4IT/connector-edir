# 06 — Search strategies and sync strategy

The four search strategies share a solid skeleton: a per-operation instance (created fresh in
`AbstractLdapConnector.chooseSearchStrategy`/`getDefaultSearchStrategy`), no state shared across
threads, and a deliberate, well-commented `next()`-before-`close()` dance to avoid spurious ABANDON
messages (MID-7091). The mutable fields (`cookie`, `lastListSize`, `retryAttempts`, `connection`)
are all per-instance and per-operation, so I found no thread-safety problem. The problems are
concentrated elsewhere: nothing in any of the three paging strategies is protected by `try/finally`,
so a `RuntimeException` from the ConnId handler leaves the `SearchCursor` open and the LDAP search
un-abandoned; `DefaultSearchStrategy` re-issues the identical search forever when the server answers
`referral`; `SimplePagedResultsSearchStrategy.finishSearch()` fires an unpaged full search whenever
the paged search ended normally; and two strategies silently truncate a result set while still
reporting it as complete. On the sync side, `ModifyTimestampSyncStrategy` derives its token from the
*client* clock while comparing against *server* timestamps, leaks its `EntryCursor` on every error
path, and — now that it is the only surviving sync strategy — makes deletions permanently invisible
to LiveSync.

Timestamp handling itself is correct and does not need fixing: `GeneralizedTime(Calendar)` sets
`upTimeZoneFormat = Z` and `toGeneralizedTime()` clones the calendar into GMT before formatting, so
the token is UTC regardless of the JVM default timezone; and `toGeneralizedTimeWithoutFraction()`
truncates rather than rounds, so the `>=` filter re-delivers same-second changes (duplicates) rather
than dropping them.

## Findings

- `major | src/main/java/com/evolveum/polygon/connector/ldap/search/DefaultSearchStrategy.java:145` | on `resultCode == REFERRAL` the branch only logs and falls through to the bottom of `OUTER: while (true)`, so the identical `SearchRequest` is re-sent until `incrementRetryAttempts()` blows up after `maximumNumberOfAttempts` (default 10) round trips and throws the unrelated `ConnectorIOException("Maximum number of attempts exceeded")`; on a partitioned eDirectory tree a base DN whose partition is not locally replicated hits this on every search. The `Referral referral` local at line 77/146 is assigned and never read, confirming the branch was never finished. | `break` out of `OUTER` after logging the ignored referral (as SPR and VLV effectively do), or surface a proper error naming the referral URL.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/search/DefaultSearchStrategy.java:104` | `handleResult()` (and the same call at `SimplePagedResultsSearchStrategy.java:134` and `VlvSearchStrategy.java:181`) can throw any `RuntimeException` — from `AbstractSchemaTranslator.toConnIdObject` or from the ConnId `ResultsHandler` itself — and there is no `try/finally` around the cursor, so `LdapUtil.closeAbandonCursor` is never reached: `SearchFuture` is never cancelled, no ABANDON is sent, and the Directory API keeps draining the rest of the result set into an unbounded `LinkedBlockingQueue` (`MultipleResponseFuture`) held in the shared per-server connection's future map. A handler that fails on entry 5 of a 200k-entry search buffers the other 199,995 entries in the connector heap. | wrap the whole cursor lifetime in `try { … } finally { LdapUtil.closeAbandonCursor(searchCursor); returnConnection(); }` in all three strategies.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/search/SimplePagedResultsSearchStrategy.java:232` | `finishSearch(...)` is called unconditionally, including on the normal exit path where the do/while ended precisely *because* `cookie == null`; it then builds an SPR control with `size=0` and a null (encoded as zero-length) cookie, which is not an abandon per RFC 2696 but a brand-new request whose paging control is effectively a no-op — the server re-runs the whole search unpaged, and `finishSearch` walks the entire result set emitting `LOG.warn("Unexpected finish SPR response (ignoring)")` per entry. Every completed paged search therefore costs a second, unpaged full scan. | return immediately at the top of `finishSearch` when `cookie == null`; only send the size=0 request when a live cookie is actually outstanding.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/search/SimplePagedResultsSearchStrategy.java:218` | when the server returns a page containing zero entries but a non-empty cookie (legal under RFC 2696, and what several servers do when a whole page is filtered out by ACLs), the loop `break`s and `search()` returns normally with `isCompleteResultSet() == true`; `executeQuery` then hands midPoint a `SearchResult(..., completeResultSet=true)` for a truncated result set, and reconciliation will treat every unfetched account as deleted. `VlvSearchStrategy.java:329` has the same silent truncation. | only treat an empty page as end-of-search when `cookie == null`; otherwise call `setCompleteResultSet(false)` (or keep paging) before breaking.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/search/SimplePagedResultsSearchStrategy.java:321` | the `finally` calls `LdapUtil.closeDoneCursor`, which deliberately throws `ConnectorException("Closing search cursor that is not DONE …")` when the cursor is not done — exactly the state left behind by the `CursorException`/`LdapException` catches at lines 316–319. The javadoc promises "most of the errors in this method are ignored … error in ending the search is not critical", but a hiccup in the throw-away finish request turns an already-successful search into a failed connector operation, and it also masks the original exception. Line 307 additionally dereferences `searchResultDone` without a null check, so an SPR finish response that arrives without a DONE message NPEs out through the same `finally`. | use `closeAbandonCursor` here (or guard with `cursor.isDone()`), and null-check `searchResultDone` before `getLdapResult()`.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/sync/ModifyTimestampSyncStrategy.java:171` | `LdapUtil.closeCursor(searchCursor)` sits on the happy path only. If `handler.handle(...)` (line 167) or `toConnIdObject(...)` (line 163) throws — which is how midPoint aborts a LiveSync run — or if either the `CursorException` (139) or `LdapException` (174) catch fires, the `EntryCursor` is never closed and the search is never abandoned, while `returnConnection` puts the connection back into use with the search still in flight. | move the cursor into try-with-resources, or add a `finally { LdapUtil.closeCursor(searchCursor); returnConnection(connection); }`.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/sync/ModifyTimestampSyncStrategy.java:216` | `getLatestSyncToken` builds the token from `System.currentTimeMillis()` (the midPoint host clock) but the token is compared against server-generated `modifyTimestamp`/`createTimestamp` values. If the connector host clock runs ahead of the eDirectory host by N seconds, every change made on the server during those N seconds carries a timestamp below the stored token and is missed forever — silently, with no error anywhere. The code comment at line 182 acknowledges the assumption but nothing enforces it. | derive the token from the server: track the highest `modifyTimestamp`/`createTimestamp` actually seen in the result set (falling back to the incoming token when the set is empty), or subtract a configurable safety margin from the client clock.
- `major | src/main/java/com/evolveum/polygon/connector/ldap/sync/ModifyTimestampSyncStrategy.java:155` | `deltaType` is hard-wired to `CREATE_OR_UPDATE` and is never reassigned; since this fork deleted the changelog/DirSync/accesslog strategies, `ModifyTimestampSyncStrategy` is the only implementation `chooseSyncStrategy()` can return, so the connector declares `SyncOp` but can never emit a `DELETE` delta. Accounts deleted in eDirectory stay active in midPoint until someone runs a reconciliation. | document the limitation on the resource definition and require periodic reconciliation, or narrow the advertised sync capability so operators do not rely on LiveSync alone for deprovisioning.
- `minor | src/main/java/com/evolveum/polygon/connector/ldap/search/SearchStrategy.java:182` | `executeSearch` returns `null` after swallowing `LdapReferralException` (and has already called `returnConnection()`), but all four callers dereference the result immediately — `DefaultSearchStrategy.java:87`, `SimplePagedResultsSearchStrategy.java:111`, `SimplePagedResultsSearchStrategy.java:302` (whose `finally` then NPEs again inside `closeDoneCursor`) and `VlvSearchStrategy.java:154` — so the "ignore the referral" path produces an NPE plus a double connection return. - `minor | src/main/java/com/evolveum/polygon/connector/ldap/search/VlvSearchStrategy.java:251` | `lastListSize` doubles as the ConnId "unknown" sentinel (`-1`) and as the value fed back into `vlvReqControl.setContentCount(lastListSize)` at line 145; after a VLV response that reports `contentCount == 0` while still returning entries, the next request carries `contentCount = -1`, outside the `INTEGER (0..maxInt)` range the VLV control defines, and a strict server can answer `protocolError`.
