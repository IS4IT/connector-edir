# 04 - connection (network edge)

`ServerConnectionPool`, `ServerDefinition` and `ConnectionManager` implement a one-connection-per-server
"pool" with primary/active/failover selection, plus TLS setup and binding. The selection logic itself is
sound (primary first, stick to the active secondary, then desperate retry) and every `getConnection()` path
ends either in a connection or in a `ConnectionFailedException` — `lastException` at
`ServerConnectionPool.java:213` cannot be null, because the desperate loop always attempts at least one
server. The real problems are on the failure paths: a failed bind leaks the freshly created
`LdapNetworkConnection` (socket plus a MINA `NioSocketConnector(1)` processor thread) instead of closing it,
the runAs variant additionally tears down the shared pooled connection, TLS is unauthenticated by default
(`allowUntrustedSsl` was flipped to `true` in this fork, commit 2869853) and hostname verification is never
performed at all because the Apache LDAP API never sets `endpointIdentificationAlgorithm` on the MINA
`SslFilter`. `ServerDefinition.parse()` is also unforgiving: keys and values are not trimmed and unknown keys
are silently dropped, so a plausible-looking secondary-server line can silently collapse into a duplicate of
the primary. Thread-safety was checked and is *not* an issue here: `AbstractLdapConnector` is a
`PoolableConnector`, `ConnectionManager` is created per connector instance (`AbstractLdapConnector.java:127`)
and there is no static state in the package, so the unsynchronised `attempt`/`active`/`downTimestamp`/
`connection` fields are only ever touched by the single thread that borrowed the instance.

## Findings

- blocker | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:435 | on bind failure `connectServer()` calls `closeServerConnection(serverDef, ...)`, but `serverDef.getConnection()` is still null at that point (it is only set at line 444), so the connected local `connection` — TCP socket, TLS session and its own MINA `NioSocketConnector(1)` processor thread — is dropped on the floor; every failed bind (wrong service password, intruder lockout, server rejecting the bind) leaks one socket and one thread, and midPoint retries these operations, so the JVM eventually runs out of file descriptors/threads | close the local `connection` in the catch block (or call `serverDef.setConnection(connection)` before `bind()` so `closeServerConnection` has something to close).
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:625 | `createSpecialConnectionBind()` reacts to a failed runAs bind by calling `closeServerConnection(server, ...)`, which unbinds and closes the *shared pooled* connection of that server and nulls it out, while the runAs connection that actually failed is leaked; one end user typing a wrong password therefore kills the connection used by all other operations and leaks a socket/thread | close the local runAs `connection` here and leave `server`'s pooled connection untouched.
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:449 | `allowUntrustedSsl` defaults to `true` in this fork, so `createTrustManager()` installs `NoVerificationTrustManager` for every `ssl` and `starttls` connection: no chain, expiry or name validation, meaning the configured bind DN and password are handed to whatever answers on port 636 and the whole topology is trivially MITM-able while still looking "encrypted" in the GUI | restore `allowUntrustedSsl = false` as the default in `AbstractLdapConfiguration` and require an explicit opt-in for test systems.
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:455 | the "secure" branch hands plain `TrustManagerFactory` managers (initialised from the JDK `cacerts`) to the Apache LDAP API, which never sets `SSLParameters.setEndpointIdentificationAlgorithm` on the MINA `SslFilter` (verified in api-all 2.1.7 `LdapNetworkConnection.addSslFilter()`), so the server certificate is only chain-validated and *any* certificate issued by any trusted CA — including one an attacker legitimately obtained for their own domain — is accepted for the eDirectory host; hardening `allowUntrustedSsl=false` therefore still leaves MITM open | wrap the returned managers in an `X509ExtendedTrustManager` that verifies the certificate against `serverDefinition.getHost()`, or build the `SSLContext` so that endpoint identification is enabled.
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ConnectionManager.java:424 | when the root DSE contains no `supportedControl` attribute (restrictive ACLs, or a server that ignores the explicit request), `parseSupportedControls()` only logs a warning and leaves `supportedControls` null, so `getSupportedControls()` returns null and `isControlSupported()` at line 397 throws NPE on every search (`AbstractLdapConnector.java:847`, `857`, `881`) instead of degrading to "no paging"; additionally each such call re-fetches the root DSE twice | assign an empty list in the warning branch so the negative result is cached and `isControlSupported()` simply returns false.
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerDefinition.java:142 | `parse()` neither trims the key/value around `=` nor rejects unknown keys, so the natural spelling `host = ldap2.example.com; port = 636` stores the keys `"host "`/`"port "`, silently falls back to the primary's host and port and produces a "second server" that is a duplicate of the first — failover appears configured but does not exist — while `port= 636` reaches `Integer.parseInt(" 636")` and aborts connector initialisation with a bare `NumberFormatException` | trim `propName` and `propValue`, and throw `ConfigurationException` naming the line and the offending key when the key is not one of the supported names.
- major | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerDefinition.java:160 | per-server `bindPassword=` is parsed out of the `servers` property, which is a plain non-confidential `String[]` `@ConfigurationProperty` (`AbstractLdapConfiguration.java:791`), so unlike the global `GuardedString` bind password these secondary-server passwords are stored, exported and displayed in cleartext in the midPoint resource configuration | drop `bindPassword` from the accepted server-line properties (fall back to the global `GuardedString`), or document loudly that it must not be used.
- minor | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerDefinition.java:239 | a numeric property with an empty value in a server line (`timeout=;` or `switchBackInterval=;`) parses to `null`, which then unboxes to NPE at `ServerConnectionPool.java:385` when the connection config is built, and — worse, because it only shows up after the first failure — inside `isAvailable()` at line 439 during failover | treat a blank numeric value as "inherit the default", or reject it at parse time with a `ConfigurationException` that names the line.
- minor | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:530 | the `GuardedString` bind password is copied into an immutable `String` and then into the `BindRequest` credential bytes, neither of which is ever cleared, so the service-account password stays recoverable from a midPoint heap dump for the lifetime of the JVM even though ConnId zeroes the `char[]` after `access()` returns | use `bindRequest.setCredentials(byte[])` built from the `char[]` and zero both the byte array and `bindRequest.setCredentials((byte[]) null)` once `connection.bind()` returns.
- minor | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:490 | connect failures are reported with `configuration.getHost()`/`getPort()` (also at line 500) rather than the server actually being contacted, so in a multi-server setup every failover error message names the primary host even when a secondary timed out, making failover incidents effectively undiagnosable from midPoint's error text | use `serverDef.shortDesc()` / `connectionConfig.getLdapHost()` and port in both messages.
- minor | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:199 | nothing ever clears `downTimestamp` — there is no counterpart to `markDown()` — so a server that reconnects successfully (in particular via the desperate loop) stays "unavailable" until `switchBackInterval` elapses, and until then every single operation first burns a full connect timeout on the dead servers ahead of it in the list before reaching the connection that already works | clear `downTimestamp` on the server whose connection succeeded, next to the `setActiveServer()` calls.
- minor | src/main/java/com/evolveum/polygon/connector/ldap/connection/ServerConnectionPool.java:442 | every bind failure, including plain invalid credentials and a `ConfigurationException` for a syntactically broken `bindDn`, is rewrapped as `ConnectionFailedException`, so `getConnection()` fails over and performs one failed bind against *every* configured replica per operation — with eDirectory intruder detection that locks the service account out across the whole topology from a single midPoint operation, and genuine configuration errors are reported to midPoint as retryable communication errors | let `ConfigurationException` propagate unchanged, and stop failing over (abort the loop) when the LDAP result was `INVALID_CREDENTIALS`.
